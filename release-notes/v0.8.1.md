# anaf-sync 0.8.1 — doar întreținere: nimic nu se schimbă pentru tine

**Dacă folosești deja 0.8.0, nu ai ce actualiza.** Programul e identic: aceleași
comenzi, aceeași aplicație, aceleași pachete de descărcat. Versiunea aceasta
schimbă numai fișierele care construiesc programul pe serverele de build, nu și
programul în sine. Am publicat-o ca să treacă odată prin lanțul de release cu
schimbarea aplicată, nu pentru că ar repara ceva ce ai fi putut păți. /
A maintenance-only release: the sole change is to the CI workflows. The
published package is functionally identical to 0.8.0 — nothing an operator can
observe differs, and there is no reason to upgrade.

Tot ce a venit în 0.8.0 — instalatorul pentru Windows, imaginile de disc pentru
macOS (Apple Silicon și Intel), comanda `anaf-sync` inclusă în fiecare pachet —
e descris pe [pagina versiunii
0.8.0](https://github.com/robert-malai/anaf-sync/releases/tag/v0.8.0), și
rămâne valabil întocmai.

## Internal

- **A `cache-suffix` per workflow (`ci`, `release-gates`, `bundle`).** Every tag
  logged `Unable to reserve cache` on the Linux bundle: `gates` in `release.yml`
  and the Linux leg of `release-tray.yml` derive an identical `setup-uv` key —
  same runner image, same 3.13, same lockfile hash — and since `bundle`
  deliberately does not wait for `gates`, both reserved it at once and the loser
  warned. `ci.yml` collided the same way, because pushing a release commit to
  `main` and pushing its tag moments later is one gesture in practice.

  Nothing was broken by it; whichever job won saved the cache and the rest
  carried on. But a warning that recurs on every release and that nobody can act
  on is one people learn to scroll past, and this pipeline has already had three
  tags (v0.5.0, v0.6.0, v0.7.0) reach PyPI with no release page while the
  evidence sat in exactly that kind of noise.

  The cost is more cache entries holding near-identical content, which GitHub
  evicts by least-recent-use; the release and bundle namespaces will be the cold
  ones between releases. Expect this run, and the first run of each workflow
  after it, to miss the cache once while the new keys fill.
